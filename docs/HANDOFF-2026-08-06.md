## Quota clarification

At the time of migration, Service Quota `L-DB2E81BA` (Running On-Demand G and VT
instances) was effectively **4 vCPUs**. Each xlarge GPU instance consumes 4:

```text
one generator GPU                    = 4
one embedding GPU                    = 4
final simultaneous setup              = 8
old generator + new generator + embed = 12 (temporary overlap only)
```

A request for 12 was opened only to allow no-downtime migration. It is not the
steady-state requirement. If the quota is now 8, that is sufficient; cancel or
ignore the 12 request unless overlap/headroom is intentionally desired. Check

## Important migration fixes already made

1. L4 memory was already about 21.7/23 GiB used, so BGE-M3 could not share it.
2. ECS GPU reservations are whole physical GPUs; separate services were used.
3. `g6`/`g6e` zonal capacity failed; a prioritized `g5` fallback launched.
4. The task landed in `us-east-1f`, which the ALB did not initially cover;
   enabling all compatible ALB subnets fixed `Target.NotInUse`.
5. A10G/SM86 rejected FP8 KV cache; mixed hardware now defaults to BF16.
6. A vLLM `--api-key` argument exposed the token in CloudWatch startup logs.
   The secret was rotated, the affected stream deleted, and tasks now receive
   the token only through the environment secret `VLLM_API_KEY`.
7. The vLLM image lacked a `python` alias; health check now uses `curl`.
8. ALB drain delay was reduced from 300s to 30s for development replacement.
9. A stuck CloudFormation/ECS deployment was recovered by scaling the service
   to zero, placing the ASG host in standby, cancelling/rolling back, then
   redeploying while preserving the downloaded model cache.
10. Do not print, retrieve, or repeat any API-key value.

## S3/Airflow design to implement later

```text
S3 versioned bucket → S3 event → SQS + DLQ → Airflow DAG
  → ECS ingestion worker → parse/chunk/hash
  → BGE-M3 endpoint → OpenSearch bulk upsert
  → DynamoDB manifest/status
```

Airflow is the orchestrator, not the embedding server. It may call the live
embedding endpoint for small batches, but must use bounded concurrency, an
Airflow embedding pool, retries, timeouts, idempotent content hashes, and
deterministic chunk IDs. For frequent/large ingestion, use a separate batch GPU
embedding service so online FastAPI latency is protected.
